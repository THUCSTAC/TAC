## 各次培训摘要

### 1. 新上岗助教朋辈分享（线上 0314）

开场暖场/自由交流，以答疑互动为主。与谈助教为陈嘉杰、陈晟祺、刘润达、张宇轩等不同课程的资深助教，会同步介绍本学期后续助教研讨计划和提供录屏供补学。

讨论话题：

- **大语言模型对助教工作的影响**: 暗中观察同学用大模型的典型用法（题目粘贴给对话模型、VSCode 等集成大模型、答疑时选中代码模型自动解释）。大模型怎么用、让不让用，很多老师在讨论但无定论。同学时间压力大，但如何培养能力？在计算机系统概论这类书面作业较多的课程，同学会优先问大模型，有同学把生成内容原封不动搬上来（只看结果大概能拿 85% 分）, 但考试时就不太清楚怎么做。近一两年大模型 reasoning 能力增强，对作业影响更大，能解决更多问题。
- **教会同学调试为什么这么难**: 调试是像扳手一样需要花时间学、花时间用的工具，回报在未来，同学很难意识到其必要性。大模型出来后能帮同学"查手册找命令", 甚至像水晶球一样给出大概思路/方向，对低年级、难度不高的作业很有用; 但对针对问题本身的深入调试，仍需同学逐行深入思考，大模型目前无法替代。这已是正向变化（降低学会调试的成本）。还探讨了能否构造与 "调试方法论" 相关的 prompt, 让模型做方法论而非细节问题。
- **有什么让助教工作更愉悦的小妙招**: 具有成就感; 终极问题是 "你为什么要当助教"; 各种自动化小工具（学生数量很大）; 不是 "教学生学" 而是 "带着学生学"。
- **助教工作里最耗时间的任务**: 书面作业的出题/批改、写题解（写题解有时也挺愉快）; 一种方案是每次只批改三分之一同学的作业; 但整体流程最长的其实是设计新作业/实验（可能几个月）; 答疑容易被忽略但整个学期累计很长; 批改考试卷（集中在考试周）; 参与课件制作等。
- **最让人愉悦/心累的事**: 心累的主要是抄袭相关、态度不端正（完全摆烂）、把成绩登错了。

（附：2024 春 "助教工作效率技巧和常见误区" 的部分内容供参考。）

### 2. 如何做好答疑辅导 (0411)

- 相关计算教育研究：SIGCSE2023 Student Expectations of Tutors, SIGCSE2024 just in time teaching tips for tutors。
- 一些程设课程使用 AI 辅导的尝试（哈佛、UC Berkeley）。
- 反馈问卷; 自我介绍 + 随机聊一个与答疑相关的话题（"我们课上同学主要通过什么渠道求助""同学们最常问的问题是什么"）。
- 介绍 Stanford CS198 的 Debugging Interview Preparation Worksheet（调试策略、概念理解、理解学生代码、与学生有效沟通、让学生舒适）, 讨论这些对程设之外课程是否适用。
- 答疑中可能出现的情形：被同学问住、对前置知识不熟悉、突然想起之前答错、如何避免 "阴阳怪气" 而不自知、被挂树洞/朋友圈; 推荐《非暴力沟通》。
- 线上 vs 线下答疑; 微信答疑为何不受欢迎（边界感、随时期待回复）; 制定 QoS 规则; 海外 office hour 制度; 让同学对助教的答疑方式有明确预期。
- 为什么很多同学遇到困难不会求助; 如何安排好一学期的答疑; 大语言模型能帮忙答疑吗。

### 3. 如何教会同学调试 (0417)

- 介绍更系统的调试方法：Delta Debugging（自动简化测试用例，出自 Why Programs Fail Chapter 5）、Statistical Debugging。
- 材料：Debugging book、fuzzing book、David J. Agans《Debugging: The 9 Indispensable Rules》、G. Aaron Wilkin《Debugging From Art to Science》（列出了教学目标，如描述缺陷如何产生、按可复现/确定性对 bug 分类、阅读和理解大型项目、重现/强制失败的过程、用科学方法搜索 bug、高效利用调试工具、用因果规则修复并证明修复、设计技术/模式以简化未来调试; 并让学生做 bug logbook）。
- 讨论：自己从哪里学会调试; 同学们学会调试的难点。
  - 自己学会调试：分布式/并行系统难以重现、涉随机; 图形学以输出调试为主; 硬件调试主要看波形（进阶做法如与模拟 ISA 对拍）; 最小化代码 / minimal working example 复现; 有人当了助教才自学 gdb, 发现 gdb 这么好用。
  - 同学学会调试的难点：不善于使用搜索引擎; 缺乏 "找中间状态和预期状态是否一致" 的思路（gdb、printf、dump 本质都一样）; 本科课程没有系统教过调试; 写码欲望下降、潜意识里想要现成框架, 而从零开始写框架其实是珍贵的调试学习机会。
- 大语言模型能帮助同学调试吗：讨论并提出了 "出一点反大模型的作业""以足够大的开源项目为学习方法" 等思路。对 "摆烂型" 同学可能遇 bug 直接躺平; 也可能已常驻 copilot/cursor 等工具。
- 通过作业/文档教会调试的尝试：Stanford CS107e LAB3、清华网络原理调试文档、计算机组成原理错误速查清单、数据结构 "调试辅导课"（前半学期每周一次 20-30 分钟, 分调试概论、代码风格、测例构造三节——因为线下答疑难以克服代码难读、工具不熟、调出后没建立信心等问题）; 也有助教给课程加了用 vscode 调试的文档、在 PA 文档里开一节。
- 调试竞赛：算法竞赛，但是要求限时调代码（Competitive Debugging）。
- 暖场：自我介绍 + "我最近遇到的一个有趣 bug 是..."（可以是自己写的，也可以是课上的；程设、数电、OS 用户态/内核态切换未考虑浮点寄存器、windows 驱动调试等）。

### 4. 计算机教育与游戏 (0508)

暖场：我担任 xx 课程的助教，我最近玩的一种游戏是 xx（可以是电子游戏、桌游、玩具）。讨论它与课程如何结合：

- 数据结构/计算思维：三国杀（维护牌堆的数据结构？实现三国杀 AI？）
- 程序设计基础：中国象棋（实现象棋游戏？象棋 AI？），若完整实现太困难，可给出一个象棋程序，让同学尝试加村规；也用 leetcode 的积分/徽章/排行榜作为参考
- 操作系统：阴阳师（回合制卡牌对抗，五个角色的行动顺序/速度类似进程调度/并行，有些技能改行动条就像进程提升优先级）
- 用贪吃蛇游戏呈现算法；一学期同学独立写游戏可能较难；给一个养成/换装类游戏如何优化、应用一些技术；scratch 写游戏；乐高编程

讨论/脑洞：

- 游戏设计与开发本身，是否值得作为一门计算机专业的选修课？（可能还涉及美术，更适合多专业通识课; 学校有未来动漫/游戏社团）
- "绩点排名""相对性能给分" 是否也属于 "游戏化机制"？为什么没有让大家感到 "好玩"？—— 打输游戏的惩罚不同；平常玩游戏是一种可选行为，但绩点排名是必须的选项，心理上完全不同。
- 小组互评？一对一 battle？类似 LLM arena 的竞技机制——不是给其他小组作业打分数，而是比较两个作业的相对优劣。
- 游戏里让人上瘾的"奖励机制"（任务是你可以完成的、社交机制）如何融入教学："我 AC 了一道题目，你也来试试吧！"、"80% 的同学通过了这道题目的九成测！"、"恭喜你，程序性能打败了 1% 的同学！"、"分享你的测试结果到朋友圈"、"通过全部题目，获得本课程的白金奖杯成就"、"游戏联动课程"的实体奖牌/经典台词/表情包。也要让不喜欢这种机制的同学保持舒适（一键屏蔽），以及如何反沉迷。

**不插电的计算机科学** (csunplugged)：面向小学生入门二进制。脑洞——如何设计一个这样的活动，呈现我担任助教的课上的一个知识点：

- 数据结构：平衡树用球棍积木搭建，通过拆装积木来实现旋转
- 数据概论：几个表的合并做成卡片，讨论如何合并几张表
- 操作系统：内存分配用卡片表示内存，尝试密铺、减少碎片；做一个比赛——生成随机的内存分配操作序列，看谁能放更多的轮数
- 程设：指针/链表——每个同学头上贴一张白纸，扮演一个变量（纸上写数据）、指针变量（纸上写 x 行 y 列，对应某个同学的座位）、链表节点；更进阶可以让每个同学扮演一个二叉树节点

讨论：游戏为什么吸引人？为什么我玩游戏会感到开心/不开心？能否迁移到课程？

- 开心：低成本获得某种在现实中很难获得的体验（如 FPS）；主要是有反馈，且反馈比较快；低年级课堂缺少类似的小步快跑反馈（后八周一整个大作业反馈太慢）。
- 不开心：重复去做、打完失败还要回来，非常枯燥、没有成就感、很耗费时间；必须做一些无聊的任务（部分地方会卖数值）；回报与投入不成正比——付出很多时间做的作业，和别人随便抄一抄的作业分数一样。
- 迁移思路：让学生低成本学到某种课外很难学到/接触到的东西；但学生仍需理解一套基本的概念术语，才能知道如何搜索和提问。

### 5. 中小学 CS 与 AI 教育 (0512)

- "小孩子学打字需要'儿童特制键盘'吗？"（《安德的游戏》桥段）, 引出对面向儿童/中小学教学设计的思考。
- 活动："假设把我当助教的课程，给没有编程基础的高中生进行科普，可以从什么方向入手？"
  - 数据结构：用点 scratch 之类的可视化编程，展示排序等基本算法。
  - 计算思维：这门课本身不需要很多修改，本来就面向没有编程基础的大学生；可视化很重要；可使用 AI 进行现场讲解/编程演示——现在的高中生用 AI 编程，能生成比我们当时大一写得更复杂的程序。
  - 计算机文化基础：数据处理相关内容，例如分析高中生的成绩，用可视化/自然语言呈现；数据分析和高中统计概念能衔接，可让高中生尝试软件、简单 python/R。
  - 数电实验：有编程基础的同学可能都不感兴趣，首先要尝试说明硬件系统知识的基础性（搭数字电路的游戏？Turing complete）。
  - 工业数据挖掘：内容与互联网产品设计相关，较多文科同学选课、较通识；曾让同学用大模型搭一个智能体，这个作业挺有意思；以及关于把 OI 同学吸引到大学计算机专业的一些想法（回到母校讲座，把"没那么好的地方"也说给同学听）。
- 讨论浙江新高考技术科目（信息科技）真题的难易、能否推广到更多省份；2022 年新课标如何落地；GESP 分级大纲能否验证儿童学习编程的效果、按大纲教学能否激发兴趣；如何看待"少儿编程热潮"是否可持续。
- 拓展阅读：Papert《Mindstorms》（Logo，让儿童通过编程学会数学）、落日间的给高中生游戏制作课、《义务教育信息科技课程标准（2022 年版）》、教育部《关于加强中小学人工智能教育的通知》（2030 年前在中小学普及人工智能教育）。

### 6. 编程作业的创新设计 (0515)

本次以一门新课程——**Rust 小学期**为例，讲讲它是如何从无到有设计出来的，以及三年来的变化。

**背景与设计思路**

- 背景：多门课程引入了 Rust（操作系统、编译原理）。小学期改革后，变成大一 4 周程序设计训练（Python/Rust/Java），汇编语言程序设计挪到秋季学期的计算机系统概论。目标：4 周内完成"学习一门新编程语言 + 锻炼编程能力"的双重目标。
- 设计思路：课上主要讲语法（从基础到复杂）；小作业先让同学用 Rust 重写一遍以前用 C/C++ 写过的程序，逐渐引入 Rust 的特性、体会 Rust 的不同，以巩固上课内容为主、不考虑区分度；大作业第一个主要考察 Rust 语法和标准库（Bonus：用第三方库可极大降低难度），第二个主要考察基于第三方库用 Rust 开发大型程序；每个大作业内设置难度阶梯、有一定区分度。

**小作业（分阶段）**

- 第零阶段：环境配置作业（WSL + VSCode + Git）。
- 第一阶段：写一遍以前写过的 C/C++ 代码，保证学生知道怎么实现，只需要把语言"翻译"到 Rust，从 C-like Rust 写起——学生："啊，我会写 Rust 了！"
- 第二阶段：开始引入一些 Rust 语法，教学生如何用 Rust 特性简化代码——学生："啊，Rust 好用，可以简化代码实现！再也不写 C-like Rust 了！"
- 第三阶段：引入 Rust 最难的部分——所有权和借用，锻炼新的思考方式——学生："啊，Rust 好难，我死了！"
- 第四阶段："放水"。此时大作业已布置，同学们没心思放在小作业上，就照着上课内容布置一些简单题目让大家乐呵一下。
- 课堂练习：每次上课结束布置一次小作业，夹杂当天讲的语法点的小练习；提示用什么语法实现，但不做强制要求、允许绕过、不扣分。
- 小作业评分：20 个 OJ 题目、每题 1 分，占总评 20 分；从布置到截止三天，不查重、送分为主；超过 DDL 按时间扣分。用本地 Git 管理题面和数据，用 Python 脚本同步到 OJ 平台、抓取提交结果、统计分数并生成网络学堂打分 xls。

**大作业**

- 前两周：Wordle 大作业（编写一个游戏，主要考察 Rust 标准库编程，初始不够 Rust-y、较 C-like）。
- 后两周：OJ 大作业（编写一个在线评测系统，主要考察基于 Rust 第三方库的网站开发，考察对陌生第三方库的学习和理解能力；第三方库先由学生自学，后由助教通过两次习题课帮助学生渡过难关）。
- 评分分三部分：基础要求（必须实现、分多步、必须按顺序实现、提供自动化测试，同学能自己预知能拿多少分）、提高要求（多个不同方向，学生可选实现哪些，由助教验收打分，但得分设上限、不能弥补基础要求失分）、非功能要求（代码规范、Git 代码管理、作业报告）。分数占比：第一个大作业 60+20+20，第二个 40+40+20；平均得分 75 左右。
- 大作业验收：每位学生 10 分钟验收大作业进展，对着代码讲解和演示各功能要求；抄袭与否一目了然（抄袭的同学讲不出代码做了什么事）；锻炼展示能力（后续许多课程都会用到）。验收结果记录在共享表格，下载成 csv 后经 Python 脚本处理出成绩，用 git 管理成绩历史、避免手算；总评也通过脚本计算；公布后提供复议机会。

**AI 小作业**

- 去年讨论过一个 AI 提示词作业：让同学输入提示词，让大模型生成可以通过 OJ 的 Rust 代码。24 年暑假加了不计分的 AI 小作业，但参与的人较少（只有十人），可能需要更有意思的形式。

**讲讲故事**

- Rust 小学期课程主页：https://lab.cs.tsinghua.edu.cn/rust/ 。
- 未来：继续调整课程内容和作业内容；大作业的抄袭现象逐渐显现，该三年一大改了；"退休"，交接给新一代助教。
- 课堂讨论：关于作业设计的脑洞/困惑 + 每门课"我们课程布置的编程作业形式是什么"的自我介绍；也再次引入 2024 秋"造路由器"作业的迭代作为对照案例。

### 7. 如何收集和分析学生反馈 (0520)

- 助教如何参与调研和课改（沿用 2024 春材料）。
- 计算机系统概论 2023 秋季学期案例：学期后段压力变大，通过无声/有声反馈（作业平均分下降、群聊抱怨）感知; ddl 十天内完成批改并写题目解析，让大家查缺补漏; 因批改慢、题解发晚半天，同学在群里催; 该习惯从那一届开始提供题解，过去是考前找助教交流; 也讲两个课堂进度同步、如何给后续课程（编译、OS、计原）作铺垫; 茶园计算机系统概论用双人组队做更有趣的实验。
- 收集反馈的方法：利用作业在线平台统计数据（git commit history、平台日志、甚至完成作业的键盘数据）; 在实验报告要求写完成感受、想法和完成用时; 助教平时答疑中了解意见; 期末问卷问 "你最喜欢/最不喜欢的作业题目是什么、理由"。

### 8. 作业评分与查重 (0522)

课件 by 陈晟祺（与 2024 秋第九讲同源，更新为当学期版本），核心内容参见 [2024 秋 作业评分与代码查重](../2024A/index.md) 的完整记录。要点：

- 选做与必做：无论黑盒还是白盒，在规模较大时都可设置选做项目（分数）。例如黑盒 80%（基础要求 60% + 提高要求 20%），提供合计约 50% 的可选分；白盒选做可作为加分（如代码风格明显优秀）。
- 必做项目着重考察课程基础内容；详细描述要求、控制难度，给学生成就感；注意内容的递进和依赖关系，防止学生 "卡住"。
- 选做项目作为提高要求，可适当发挥；提供多个不同方向，按难度给分；可留出开放内容，给感兴趣的同学探索空间（谨慎提供分数奖励）。
- 必须严格控制总分，不要留下内卷空间！
- 评分标准：必须预先确定并使用统一标准；每个赋分要求应详尽规定；不推荐主动抹平区分度；是否公布详细标准需权衡——过于含糊学生难以预期，过于详细易过拟合、学生和助教都失去自主空间。
- 评分反馈应及时且详细；推荐做法是列举所有可能的评分点，批阅时详细标注，再根据规则计算分数并生成对应评语；善用公式/脚本自动化生成重复部分、内置检查规则。
- 迟交处理：以基于迟交时间衰减赋分的折中方案平衡 "宽松→拖延" 与 "严苛→冒险抄袭"；无论何种方案都应在课程开始时（任何作业开始前）确定并明确告知。
- 组队作业：不同组队方式的利弊；组员数量不同可采用比例折扣；组内工作量不均可通过验收逐个提问、全过程评价与及时干预缓解（CATME、SIGCSE 2023/2022 的组队评价论文）。
- 查重：不是为了不相信同学，而是维护学术诚信；典型往年代码/讲解录像/Copilot 案例；工具 Stanford MOSS、JPlag、JiePlag（@jiegec 重写）；分析流程与约谈、algorithms 判断核心准则。
- 编程作业分数划分：黑盒（客观、可自动化、70%-90%）与白盒（主观、人工评判、10%-30%）；黑盒中是否公开测试用需权衡，推荐公开部分 + 隐藏测试；可设性能分但防内卷；自动化评分方案由简到繁；白盒也应明确评分项目与标准避免助教间偏离过大。
